# Comprobar una candidata antes de main

El workflow «Complete gate and Chromium startup orders» conserva el archivo histórico chromium-startup-order.yml, sus eventos push a main por las rutas originales y workflow_dispatch. Mantiene la matriz conquest/native en runners separados y ambos archivos completos en cada orden. El hash de Chromium se registra después de las pruebas; antes solo se consulta metadata, sin leer su imagen ni ejecutar warmup. Los experimentos históricos de precarga conservan su significado diagnóstico en sus propias ramas.

Se añade un job completo clonado de offline-browser.yml: exactamente `node validate-release.cjs --report "$RUNNER_TEMP/release-validation.json"`, mismo Node24, runner, módulos públicos hash-pinned, OVERLAY_BROWSER_REQUIRED=1, timeout15min, permisos contents:read y artefactos. No usa filtros, precargas, overrides ni relajación de checks. Cada ejecución del workflow conserva los dos jobs de orden y exige además el gate completo. El CI automático offline-browser de main también sigue activo.

Una candidata comprometida en una rama puede ejecutar `gh workflow run chromium-startup-order.yml --ref <rama>` sin crear PR ni mensajes externos. El paso manual no publica ni sustituye el gate local, la revisión independiente o la concurrencia. Solo es válido para el SHA exacto ejecutado. Antes de main, comprobar que ese SHA coincide con la candidata final y que todos los jobs terminaron correctamente. Cualquier cambio posterior exige validar el nuevo árbol. Después del push normal a main, comprobar nuevamente los workflows automáticos exactos y los bytes servidos; el pase previo no garantiza otro runner ni repara por sí mismo almacenamiento inestable.

Cada informe debe indicar SHA, resultado real y límites. Este workflow no acredita una sesión de juego. Los tres jobs hacen explícita la cobertura: el gate completo se añade a los órdenes; no se retira ningún archivo ni aserción original.
