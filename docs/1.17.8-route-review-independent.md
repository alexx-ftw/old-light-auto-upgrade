# Independent review: repeated route review

## Result

No blocking issue found in the bounded production diff against `a45e735`.

The new `waiting` classification is restricted to an explicit denied result from
the initial ally guard, the `ownership` or `unknown-owner` code, and a `route:`
mission ID. It occurs before native target resolution, preparation, or dispatch.
It does not turn an arbitrary exception or later guard failure into an automatic
retry. The new waiting message accurately describes the route as active but
blocked until ownership can be verified.

## Safety findings

- The review identified that the attempted-claim check originally followed the
  initial guard. The final patch moves it ahead of that guard. An accepted or
  unconfirmed native click therefore remains `uncertain` if that same claim is
  presented again while ownership evidence is unavailable.
- An initial failed check has issued no approval token to preserve. Once the
  initial check succeeds, the original owner, epoch, generation, coordinates,
  and scope token continues through the existing later checks. Census loss
  during target resolution, preparation, quantity input, or final click still
  pauses. Owner, epoch, and generation changes still require review.
- Protected targets, unresolved aliases, invalid scope, storage failure, and
  ordinary or retry-campaign jobs retain their prior blocking behavior.
- The real route engine, durable queue, and native adapter preserve one ticket
  through repeated initial census failures. Queue backoff remains effective;
  recovery produces one accepted send and the normal interval cooldown.
- Existing pending reviews are intentionally not cleared. Their persisted state
  cannot prove that no native send previously occurred.
